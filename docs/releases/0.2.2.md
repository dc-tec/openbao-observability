# OpenBao Observability 0.2.2

OpenBao Observability 0.2.2 uses OpenBao 2.7.0 as its reference profile and
verifies compatibility with OpenBao 2.6.3. It corrects seal-state normalization
and authorization-denial queries, and expands fixture coverage for both releases.

## Highlights

- Scrape adapters preserve the sealed startup signal. Recording rules select
  one seal-state source per target when startup and unsealed samples overlap.
- `OpenBaoCoreUnsealedSignalMissing` reports successful scrapes without a
  seal-state metric. OpenBao 2.6.3 can stop emitting the gauge while sealed;
  OpenBao 2.7.0 keeps refreshing it. A missing signal remains unknown.
- Audit queries count policy-template denials from the request audit entry.
  The captured response has HTTP status 400 and a generic audit error. Ordinary
  ACL denials count once, from the response entry.
- Fixtures check malformed identity metadata, canonical policy paths,
  unseal/reseal transitions, sealed restart, and recovery. The 2.7.0 Raft
  fixture also checks consistency headers, retry responses, and forwarding.
- The PostgreSQL 18 Compose volume uses the image's current data-directory
  layout, fixing startup of the default evaluation stack.

## Upgrade notes

Apply the updated scrape relabeling and generated recording rules together.
The adapters use the bounded `seal_state_source` label to preserve the startup
sample. The rules remove that label after selecting one state per target.
An older adapter that drops the startup sample cannot report sealed startup.

Sealed-node metrics require the private unauthenticated metrics listener.
The authenticated metrics endpoint does not become available while sealed.

The PostgreSQL volume now mounts at `/var/lib/postgresql`; PostgreSQL 18 stores
its data under `18/docker`. Migrate older data or reset disposable evaluation
volumes before using this layout. A Compose reset deletes all volume data.

OpenBao 2.6.3 and 2.7.0 fix malformed-input audit leakage in built-in plugins.
Upgrading does not sanitize stored audit records. External plugins need a
patched SDK build; see the
[upstream advisory](https://github.com/openbao/openbao/security/advisories/GHSA-8xxq-mq9m-xmhw).

## Compatibility and validation

CI captures and verifies OpenBao 2.6.3 and 2.7.0 independently. Both `vault_*`
and `openbao_*` metric prefixes remain supported. Prometheus rule tests cover
seal-state alert firing and recovery, overlapping samples, missing signals,
and separate deployment identities.

The 2.7.0 implementation was also checked against the local Compose stack:
all 253 dashboard queries passed live validation. The consistency fixture
uses a future index to exercise protocol behavior; it does not measure
replication lag or establish a production latency objective.

This release remains a reference architecture and implementation profile.
Fixture coverage does not establish a production support commitment.

## Dependency and profile updates

The default Compose profile uses OpenBao 2.7.0, PostgreSQL 18, Prometheus
3.14.0, Loki 3.7.8, Grafana Alloy 1.19.2, and Grafana 13.2.2. The Go module
uses OpenBao API client 2.7.0 and Prometheus 0.314.0.
